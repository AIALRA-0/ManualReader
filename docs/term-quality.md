# 术语怎样用两段独立讲清楚

第一段是定义，至少 80 个非空白字符：讲清它是什么、为什么需要它，以及它怎样起作用。必要的新概念在使用处说明，不能只用几个专业词代替解释。

第二段是直观解释，至少 100 个非空白字符：抽象机制使用能想象的具体场景，把对象、动作和结果接回真实机制；生物或物质优先描述可观察的外形、行为和变化。两段相互补充，脱离原文章也能读懂，不靠重复、无用辨析或堆背景达到下限。

完整生成规则保存在 [reader_term_quality.py](../reader_term_quality.py) 的 `INSTRUCTION`。讲解与问答提示词、`/api/guide` 的 `term_quality` 及下载的 Agent 客户端使用同一份规则。模型在同次写作中完成两段，检查不调用另一个模型。

# 旧术语怎样补齐

`GET /api/terms/audit` 返回 `content_quality`，其中 `repair_fields` 标明过短、依赖文章或完全重复的字段。已经合格的条目复用原 ID；只补一段时，另一段原有的合格内容与排版保留。

`POST /api/terms` 的 `updates` 中提交原 `term_id`、当前 `expected_version` 和需要修改的字段；可附 `expected_definition` 与 `expected_intuitive_explanation` 核对旧文本。同一批次先全部检查再写入；任何编号、版本或内容冲突都拒绝整批。成功后旧解释进入 `definition_history`，名称、关联、笔记、练习和手动阅读记录保持。

只改名称的既有接口继续使用名称规则，不会触发解释重写。新术语与明确重写的当前版本术语接受完整检查；旧项目读取不会因为短术语被阻塞。

# 怎样复现检查

运行 `python -m unittest Demo.test_term_quality -v`。测试使用合成数据，覆盖两段最低长度、独立性、旧条目复用、字段选择、版本冲突、旧文本冲突、历史保留及真实 HTTP 批次的原子写入。

字数下限可以挡住过短内容，不能证明解释准确或例子易懂；这些仍要结合真实生成样本阅读验证。检查保留报告，不会用脚本盲删包含“不能”等字样的知识内容。
