## 哪些检查实际执行了

- 在最终 High 合同下，七个已完成的三案例调用共返回二十一个案例，全部通过编号、引用、参数、前置登记和练习位置检查；另一个长批次在上游连接两次重置后停止，随后按 Reader 实际逐章粒度复测；其中两份直接通过，一份由脚本修正前置编号格式后通过，未重写正文
- 九份 Python 代码按实际输出执行；Verilog 顶层请求选择执行九十六组测试，正确实现全部通过，故意放入的错误优先级被测试拒绝
- 同样的完整章节、四张原图和十八条问题进行了多次真实生成；另用正式 `daily` 入口跑三条已保存问题，验证领取、两路生成、写回和主调度汇报，不触碰原项目
- 八个隔离 Reader 项目实际点击问答与练习，并检查五种尺寸，包括手机横竖屏；公开仓库的确定性检查可用下面的命令重跑

## 同样十八题的用量怎样变化

原版已知写作窗口为1178.236秒，输入7889724、其中缓存输入7267840、输出130192，文本 API 单价折算3.272472美元；新版未复用已打开来源的写作窗口为778.510秒，输入6284048、其中缓存输入5754240、输出75351，折算2.388550美元；新版干净 Low 主调度从启动到最终汇报790.277秒，另计输入28403、缓存21504、输出889，折算0.024838美元

缓存输入是输入的一部分，推理输出是输出的一部分，均不重复相加；原版主对话混有开发和维护，无法可靠单列，因此上述新旧写作费用按相同的写作者范围比较，新版主调度另外列出，没有填成零

启用同项目来源复用后，首稿已知文本折算1.923391美元；本次旧检查误报还额外花费约0.090786美元，这笔费用保留，当前检查已用原稿回放修正；API 缓存不能主动清空，这里的冷热指来源缓存是否启用，实际缓存 Token 照常记录

也实测了 Medium 集中查证和六组三题并行；集中查证能够省去一部分重复搜索，但增加前置等待，六组三题的问答费用高于两组九题，默认没有采用这两条较重的路线

金额按普通服务文本 API 单价折算，并非 Codex 订阅扣费；图像工具、原生检索和缺失回执请求没有独立账单，不推断实际总费用；开发、压力测试与部署不混入日常阅读费用

## 为什么保留 High 写正文

Low 和 Medium 已在相同六领域材料上实际生成；Low 的名称格式补齐与 High 得到相同正确结果，适合做小范围名称修正；正文中的具体动作、关键中间状态和首次概念展开仍由 High 负责，保留用户已经认可的阅读颗粒度

写作规则、角色配置、输入缩写和检查脚本均在仓库中公开；新增模型阶段需要先证明总耗时、完整答案和费用确实改善，再加入默认路径
