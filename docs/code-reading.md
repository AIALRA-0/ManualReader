# 1 代码怎样自动着色

原文代码片段、文件标签页和 Markdown 代码块共用 highlight.js 11.12.0 的 193 种内置语法。原有材料再次打开就会采用新显示方式，不改写保存的正文、来源编号、笔记或进度。

先使用代码块注明的语言，再识别文件名、扩展名和首行解释器；没有这些线索时，先辨认明显的代码结构，再自动判断语言。SystemVerilog 使用支持 IEEE 1800-2012 的 Verilog 语法，硬件项目的 VHDL、Tcl、SDC 与 XDC 也有对应处理。

语法识别存在歧义，例如很短的代码可能同时属于几种语言。有文件名或语言标记时优先使用它们；没有匹配语法时显示原始纯文本，不隐藏或执行代码。未知语言也能阅读，但不能承诺所有自定义语言都有专用着色。

# 2 怎样避免拖慢页面

先显示完整代码，首次遇到代码时才启动同源 Web Worker 并读取语法包；阅读普通文章不会加载这个包。解析在后台线程进行，同一份代码同时出现在原文、译文和讲解时共用结果；缓存有容量上限。

着色只改变颜色，保留代码内容、字体尺寸和行高；用户正在选择代码时，等选区结束再应用颜色。解析超时或失败时保留纯文本；超过一百万字符的单个代码块也保留纯文本，避免生成过大的着色节点。文件预览原有的大小提示保持不变。

# 3 为什么选择这套开源组件

- [highlight.js](https://highlightjs.org/)直接支持自动语言识别和只读代码块；当前 Reader 已经使用过它，因此可以复用现有 DOM、复制和定位逻辑。本次把完整语法包放到后台线程，保留上游 BSD 3-Clause 许可。
- [Shiki](https://shiki.style/guide/bundles)使用 TextMate 语法，适合追求编辑器一致效果的已知语言着色；浏览器部署需要按需组织语言和主题。本次需要自动识别已有片段，因此没有另加一套着色引擎。
- [CodeMirror](https://codemirror.net/docs/)和 [Monaco](https://github.com/microsoft/monaco-editor)更适合编辑、补全和代码导航。当前需求是阅读，换成完整编辑器会增加界面和运行开销，因此保留现有阅读器。

# 4 怎样重新构建和复测

部署包已经包含浏览器资源，使用者无需安装 Node.js。维护者更新组件时，在 `tools/code-highlight` 下执行 `npm install --ignore-scripts --no-audit --no-fund`，再执行 `npm run build`；构建脚本会生成语法包并复制上游许可。

```sh
node Demo/test_code_languages.js
python Demo/check_code_highlight.py --browser <浏览器可执行文件>
```

测试使用合成文件，检查 193 种语法是否注册并可调用，以及 40 组文件、无标记片段、并发复用、选区、代码注入、长代码和八种主题尺寸组合；真实项目另通过只读浏览器验收，不写入用户记录。
