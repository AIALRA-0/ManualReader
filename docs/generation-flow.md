# 一次讲解或回答如何完成

用户在 Codex 对话里启动写作。Reader 展示已保存的正文、原文关联、练习和阅读状态。

## 哪一步由谁负责

1. 脚本按项目和章节找出原文、相关前后文、追问历史和已有术语。输入里完全相同的原文只传一份。
2. 章节和问答共用分析器。分析器根据读者已经理解的内容、当前目标和真正缺的前置，安排正文、术语、图示和练习。
3. 写作者使用 Sol high 普通服务，在同一份成稿里写正文、术语、配图和专属练习。章节按 `source_groups` 覆盖原文，每组在 `plan.coverage` 指向实际讲解段落。问答从当前问题出发，用实际引用说明原文关系。
4. 写作者查证具体缺失的事实，打开能支持结论的来源。后续写作和集中补齐可以复用本项目已读、已引用且仍相关的网页片段。图放在它要解释的正文旁边，日志摘录对照原件，逐项比较用可以选中文字的 Markdown 表格。
5. 脚本核对真实编号、问题版本、原句、参数、术语归属、练习位置和客观题计算。已有术语的名称和编号由登记表确认。
6. 脚本把合格的回答先写回。剩下的草稿保留原编号，只对已列出的缺项集中补一次。完成状态以保存回执为准。
7. 程序保存逐请求用量和各阶段时间。日志短暂被占用时，已保存的结果仍可读取；失去网络响应后可以用原任务目录重交已经通过检查的批次。

## 哪些规则能直接查看

主提示词在 [reader_prompts.py](../reader_prompts.py)，分析、补齐和连接说明在 [reader_task_prompts.py](../reader_task_prompts.py)。`/guide`、任务接口和下载客户端共用版本。已保存的讲解和回答沿用原编号，旧练习和作答历史继续可查。

写作直接解释事物、动作、机制与结果；不在正文里反驳读者没有提出的误解，也不展示字幕纠错与事实核查过程；查明的事实正常讲清，仍未查明的具体事项记录在 evidence_gaps；真实条件、用户主动要求的区别和错误选项解析照常表达；

每个讲解部分和回答部分恰好有一道专属练习。写作者用 `placement` 指向对应的正文部分，Reader 在正文和练习栏显示同一题号，读者在任一处作答都更新同一份记录

脚本分开检查每条回答。已经通过的回答先写入项目，有缺项的回答保留原稿，只交给写作者补齐一次。补齐以 JSON 字段为单位，代码、公式和表格中的换行按普通字符串传递

网络中断后，用 `reader_bridge.py resume-writeback --out <原任务目录>` 重交已经通过检查并落盘的批次。服务器识别同一任务中已保存的回答，重交不会再生成或追加一份练习

分析器会登记本次必须解释的术语。脚本从正文匹配已登记的名称和别名，复用时核对名称与编号；新术语继续使用独立定义和直观解释两段

## 怎样统计耗时和费用

普通写作默认最多两组并行。调度负责启动、等待和汇报，讲解与问答使用 Sol high 普通服务。独立汇报可使用 Sol low，已经打开的 Codex 对话继续使用用户选的模型。

每次运行分开保存真实输入、原始输出、检查结果、字段补齐、请求用量与工具调用；缓存输入包含在 input_tokens 中；推理输出包含在 output_tokens 中，均不重复相加；正文、检索往返、补齐和主对话分别列出；缺少主对话回执时完整费用留空，不用脚本的零 Token 代替；

文档中的美元金额是按公开 API 单价折算的文本费用，不是 Codex 订阅实际扣费；工具独立费用需要单独的计量证据；

## 为什么没有强制增加共享查证阶段

本轮也实测了 Sol medium 集中准备事实、再交给 High 写作；它减少了后续重复检索，但增加了成稿前的等待；因此默认仍由 High 边查边写，只由脚本复用实际打开过的来源；需要额外查证时，可以用现有 teach --research-file 传入已经查明且附来源的资料，不额外增加审稿流程；
