# 一次讲解或回答如何完成

Reader 只展示、记录和核对结果；用户在自己的 Codex 对话里触发任务，网页不自动调用模型；

## 哪一步由谁负责

1. 脚本读取当前项目和当前章节，整理原句、必要前后文、相关追问历史与已有术语；不再把整个文件追加到每一组输入；
2. 写作者使用 Sol high 普通服务，在同一次输出中完成小型 plan、连贯正文、可复用术语和带 placement 的练习；问答不填写讲解专用的章首章末或全材料证据；
3. 讲解任务附上 source_groups；连续短字幕按小组通读，代码和图表保留自身边界；每组用 plan.coverage 指向实际 part 和正文短摘，脚本恢复原编号；这个登记证明来源已经安排，讲解是否充分还要结合原文、计算和阅读验收；
4. 写作者按需搜索，并打开支持结论的来源；此前实际打开且被有效写作引用的网页短摘可在同项目内复用；缓存过期、没有相关证据或仍有事实缺口时，继续检索；旧回答不充当证据；
5. 脚本核对真实编号、问题版本、逐字来源、参数、习题位置和客观题计算；新术语先由脚本规范名称，仍有缺项才用 Sol low 批量补名称；定义和例子仍由原写作者同次写好；
6. 新生成的内部编号有空格，或前置编号误带说明时，先由脚本同步修正编号和练习引用；原句、用户问题和正确正文保持原样；内容确有缺项时，最多一次集中补齐：用字段变更补原稿，正确正文及编号保留，不再让模型重抄整份结果；没有审稿 Agent，也没有修复循环；
7. 完成的输出立即落盘；用量优先读取逐请求服务端回执；统计日志出错时保留正文，并从回执恢复统计，不重调模型；

## 哪些规则能直接查看

完整写作要求在 `reader_prompts.py`；问答和讲解分别由 `writing_method(role)` 生成；`/guide`、任务接口和下载客户端共用版本；新合同领取的任务使用同版合同写回，旧内容通过读取适配展示，编号、笔记、作答和手动已读进度保留；

写作直接解释事物、动作、机制与结果；不在正文里反驳读者没有提出的误解，也不展示字幕纠错与事实核查过程；查明的事实正常讲清，仍未查明的具体事项记录在 evidence_gaps；真实条件、用户主动要求的区别和错误选项解析照常表达；

练习只存 quizzes，经 placement 同步插入正文和练习栏，不再抄一份题干选项到 Markdown；旧稿仅在题干和全部选项均与已有练习一致时省略重复展示，原始记录不改；

## 怎样统计耗时和费用

普通写作默认最多两组并行；调度只启动、等待和汇报；独立干净调度可使用 Sol low，已经打开的 Codex 主对话由用户的设置决定，网页不会替它切换模型；

每次运行分开保存真实输入、原始输出、检查结果、字段补齐、请求用量与工具调用；缓存输入包含在 input_tokens 中；推理输出包含在 output_tokens 中，均不重复相加；正文、检索往返、补齐和主对话分别列出；缺少主对话回执时完整费用留空，不用脚本的零 Token 代替；

文档中的美元金额是按公开 API 单价折算的文本费用，不是 Codex 订阅实际扣费；工具独立费用需要单独的计量证据；

## 为什么没有强制增加共享查证阶段

本轮也实测了 Sol medium 集中准备事实、再交给 High 写作；它减少了后续重复检索，但增加了成稿前的等待；因此默认仍由 High 边查边写，只由脚本复用实际打开过的来源；需要额外查证时，可以用现有 teach --research-file 传入已经查明且附来源的资料，不额外增加审稿流程；
