# 这份稳定交接版改了什么

v0.4.8 以 v0.4.7 为基础；它保留原文、译文、讲解、问答、术语、练习和文件标签页的现有工作流，没有迁移个人数据，也没有重新生成旧内容；部署前先备份数据目录，按部署说明替换程序；不要用发行包覆盖已有数据库、原件或配置

## 读取期间怎样看清进度

首次打开会依次记录登录状态、设置、材料、阅读记录和页面准备；切换材料会先保存当前问题，再读取目标材料和记录；切章单独显示保存、读取范围、保存选择和准备页面。百分比表示已完成步骤与当前下载进度，不表示剩余时间；实际接收数据另列字节数与下载比例，无法取得总量时只显示已接收字节。

压缩 JSON 通过 `X-Reader-Decoded-Length` 提供解压后长度，浏览器用相同口径计数；旧服务没有这个头时不使用压缩包长度估算。公共模块内嵌在启动 HTML 中，避免为了显示进度增加一次启动下载。

只有带进度的 GET 读取在三十秒没有收到新数据时自动重读一次；持续收到数据就继续等待；POST 写入和授权失败不会自动重试。失败后关闭遮罩、恢复按钮并保留原项目；首次打开失败则显示重新打开按钮。导入任务没有总工作量时显示后台真实状态与等待时间，不编造完成比例。

## 后台繁忙时怎样让首页继续响应

服务器可以启动一个只负责页面读取的进程，以及一个负责导入、Agent 接口和所有写入的后台进程。页面进程直接处理材料、进度、设置及少数只读查询，其余接口交给固定的本机后台端口；浏览器地址、项目令牌和接口格式保持原样。本地单进程启动继续可用。

已保存的状态从数据库读取已提交版本，不等待后台完成整段讲解写入；首次建立状态仍在事务内再次核对，同一项目的写入继续串行。所有更改项目文件与状态的接口都在后台进程执行，避免不同进程各自持有一把无效的写锁。

排版先建立原文编号与页码的索引，保留原来的页序、坐标与分组结果；各项目独立准备，缓存使用独立临时文件原子替换。投影只修改本次独占读取的工作区正文，不再复制一份相同的大型代码材料；共享快照不参与修改。章节静态计划不持有长时间的全局计算锁，手动进度另行计算。

性能验收同时打开首页、大项目和手机尺寸页面，并持续向隔离项目写入；必须记录繁忙时的最长等待。服务器还要检查服务的内存限制和交换记录，不能只在服务空闲时测接口。只读读取不改变正文与用户记录，压力写入只针对隔离副本。

## 原文怎样只保留一份可发送的响应

页面下载界面脚本时就读取当前项目的材料和进度；主程序使用同一份结果，领取后释放启动缓存。只有 GET 读取提前，不会提前切章、修改笔记或改变已读进度。章节计划只保存材料的弱引用，主材料缓存移除旧项目后，计划缓存不能继续留住整份正文。

HTTP 编码使用 orjson，特殊旧值或运行库未安装时沿用标准编码器；已有磁盘 JSON 和数据库都按原方式保存。回归检查解析后的中文、公式、坐标、空值和数值相同。压缩仍为原来的第三级，不以增加下载量换取少量 CPU 时间。

材料版本和题干未变化时，服务器直接复用已经编码的字节，不再另存一份同内容的展示对象。缓存未命中才整理原文、编码和压缩；写作任务需要登记请求大小时仍取得实际内容。授权检查、项目隔离和版本失效继续沿用原接口。

材料与进度接口在整理正文之前核对版本并尝试复用字节；主材料缓存被其他项目挤出时，仍有效的 HTTP 字节不会因此触发一次多余的正文整理。首次冷整理另记为 material_prepare，不能把这部分时间归为网络或页面渲染。

代理在转发时写入当前时间，后端用 proxy_wait 记录到处理函数开始之间的等待。gc_pause 记录整个进程中与这段请求相交的回收暂停，包含接收连接线程；gc 继续记录当前请求线程中的回收。几个时间区间可能重叠，应按请求时间线读取，不能直接相加。

## 切章时怎样减少重复解析和连接堆积

每个请求的事务提交或回滚后立即关闭连接，少量常驻连接仍由连接池管理。切章规划先读取状态；写入事务取得锁后，只有数据库原串完全一致，才复用已解析的状态。快照只使用一次，失败也会失效；记录发生变化时重新读取，并再次核对用户提交的切章版本。

响应头增加 db_commit 和 db_close，分别记录提交与关闭的等待。垃圾回收及数据库同步策略保持原设置。连接、事务回滚、过期快照和切章竞态都使用合成数据回归；真实大项目只在隔离副本写入。

## 多项目切换后怎样控制内存和图片请求

原文、投影、工作区和章节缓存只保留最近两份项目；进度对象也只保留最近两份项目，材料仅缓存可发送的字节，避免章节缓存继续持有已淘汰的大项目。重新打开被淘汰的项目时按原文件准备，不丢内容。

顶栏的总体覆盖使用相同的字符、对象和手动记录规则，不再额外计算详情页的逐文件、逐章列表；统计详情仍完整提供这些内容。相同材料与状态版本复用计算结果，写入或原文件变化后重新核对。完整进度也按项目、状态、材料和设置版本核对 ETag；通过原权限检查后，浏览器才可复用原响应。笔记、作答和问答更新会改变版本；轮询的未变化回执继续沿用原规则。

当前原页优先请求；其他页先设置延迟加载属性，再填写图片地址。译文中的静态裁图在进入视口附近后才下载原页，离开文档的元素不继续占用观察器。裁图、放大和来源编号继续沿用现有机制。

## 打开和原文联动为什么更快

v0.4.4 先展示当前材料，材料文件树在后台读取名称；列名称与创建文件夹不再整理所有项目的正文。缓存都有容量上限，输入版本改变后重新准备，同一版本的并发请求共用一次计算。

原页图片和坐标高亮立即显示，文字层异步补齐；切页后旧请求不会覆盖新页。原页资产复用项目只读快照，资源地址包含材料版本。界面脚本和样式按实际文件内容生成版本号，上传的原件保持原字节。

材料接口提供按项目区分的 ETag。刷新时先核对服务器版本，内容没变就复用浏览器保存的完整正文；笔记和回答展开状态改变不会重传原文。响应按 Cookie、授权和材料编号区分，其他接口继续返回实时进度。练习去重仍核对同一题干与全部选项，只在一次展示准备中复用索引。

## 怎样复测长尾耗时

使用完整项目的隔离副本，以同一域名、登录、代理与浏览器执行首次打开、刷新、连续切章、问答展开和跨页定位；分别记录浏览器排队、网关等待、服务线程调度、锁等待、业务准备、资源下载和两次绘制后的时间。响应头 Server-Timing 提供 dispatch、receive、admit、lock、project、asset_meta、asset_read、encode、compress 和 reuse_wait；未执行的阶段不会出现。

工具在点击前等待元素稳定、自动滚动和往返的时间另记。页面能操作、原图已显示和文字层可选中分别记录，保留中位数、P95、最长值与慢样本。历史事件没有分项记录时，不事后编造分项。

验收只在副本写入；原项目的正文、编号、笔记、练习作答和手动进度分别核对，不为性能重新生成或迁移内容。


## 连接后怎样减少重复读取

手动触发 Codex 后，先读取当前项目的 `GET /api/guide?view=bootstrap`；这个视图提供项目、授权范围、当前章节、待答数量、模型配置及客户端清单；完整写作规则仍由客户端读取，人工调查需要时可读取原来的 `GET /api/guide`；项目权限和章节手动已读规则保持不变

客户端继续使用 `daily` 处理问答，使用 `teach` 生成当前章节；正文、术语和练习在同次写作中完成；主对话不需要重新读取整份材料、重抄正文或逐条启动写作者；主对话、客户端调度和写作者仍分别计量，不能把脚本本身没有 Token 消耗写成整个调度没有消耗

## 怎样只补齐不足的术语

用户需要维护旧术语时，运行当前项目的命令；连接方式与其他客户端命令相同：

```sh
python reader_bridge.py --base <网站地址> --material <项目编号> terms --out <独立任务目录>
```

客户端通过 `GET /api/terms?needs_revision=1` 读取需要补齐的条目，每组最多八个、最多两组同时写作，采用当前配置的 Sol high 普通服务；它只请求不足的段落；合格段落作为上下文保留，输出结构要求相应字段为 `null`；服务器接收 `POST /api/terms` 的 `repair_only: true` 更新，并核对版本及旧文字，避免覆盖期间产生的新内容

每组依次保存输入、输出结构、原始成稿、用量回执、拟写入字段和写回回执；用同一输出目录恢复时，先读回核对；已经完成的成稿直接复用，不重新生成；后来编辑过的内容保留，不能拿旧稿覆盖；旧编号、关联和修订历史继续保留；日常问答不需要额外运行这项维护

术语仍为定义与直观解释两段，分别至少八十和一百个非空白字符；内容要讲清是什么、用途及机制，例子对应实际动作；新增术语不能通过遗漏写作版本绕过检查，按已有编号复用合格术语则不会触发重写

## 怎样保留检索质量并减少重复输入

稳定的基础概念直接解释；产品、作品设定和具体规格缺少依据时，继续搜索并打开来源；纯搜索先返回简短候选；四个查询同批时保留工具要求的中等长度，打开网页、查找证据、查看图片和混合请求保留所请求的范围，不截断讲解或原文证据

同一网站、同一项目可复用已打开并在合格成稿中引用的来源片段；缓存默认一天有效；新缓存逐页核对网址与正文，旧版缓存因分块方式可能混页而不直接使用；原缓存文件和用户内容均不删除；重复打开可能是在读不同位置，不能只按网址相同就删掉证据

没有引入全文摘要、历史压缩、向量数据库或额外审稿模型；对相同工具文本做精确去重的试验收益低于千分之一，因此没有加入正式链路

## 中断时怎样保存成稿与用量

传输器读取结束时没有换行的最后一条 SSE 回执；本地客户端断开后，仍接收已经开始的上游生成并保存公开正文及回执；上游本身中断且没有返回用量时，记录为不完整，不能估成零或假定已经成功；原始输出保留在任务目录，恢复前先检查已有成稿

`term-maintenance-result.json` 分别列出本任务累计写作回执和本次新增调用；恢复任务不重复累计模型调用；缓存是输入中的一部分，推理是输出中的一部分，不能重复相加；费用只按明确的计价来源折算，没有实际账单时保留为空；主 Codex 对话的读取、启动、等待和汇报需要在最终汇报结束后另行结算

## 本地实际验证了哪些内容

- 访谈与 EXAM2 的隔离副本共十八个桌面、手机竖屏及横屏场景，实际点击问答、追问和原文联动，并检查章首问题自动保存
- 同两份大项目的六个尺寸场景，实际打开与关闭两段式术语，核对显示与页面宽度
- 二十四个真实术语的新旧对照，并为需要检索的两组增加来源缓存复用测试；所有写作均为 Sol high 普通服务，未增加审稿模型
- 本地 HTTP 模拟连接验证末行回执、客户端断开和上游异常；同一真实长日志读回的八十五次调用用量完全相同

上述交互测试仅修改隔离副本；原编号、笔记、练习作答和手动已读进度作为不变量核对；正式发布另外核对官网程序、源码提交、版本标签、发行说明与部署包；测试不会触发旧内容重新生成
